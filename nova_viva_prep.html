Tech Stack & Architecture

Why Streamlit instead of a separate React frontend + API backend?

The actual DS/ML work — prediction intervals, the classifier, SHAP — is pure Python. Streamlit collapses UI and backend into one process, so there's no API layer to design and keep in sync, which mattered against a two-week-per-project clock. The tradeoff, accepted deliberately: less visual/interaction polish than a hand-built React app.

Why SQLite instead of Postgres or a hosted DB?

Small-scale, single or few-user app — no need for concurrent high-throughput access. SQLite is one file, which makes "delete my data" literally mean "delete the file," and needs no separate database server to run or maintain.

Why Docker, and why does the volume matter?

Reproducible environment, but the real reason is the persistent volume mount for the SQLite file. Most free hosting platforms run an ephemeral filesystem — local files silently get wiped on redeploy or restart. A Docker volume sidesteps that regardless of where it ends up running.

Why run locally with a tunnel instead of Fly.io / Railway / Render / Amplify?

Each had a specific disqualifying issue at this app's scale: no free tier at all, a free-tier volume that auto-expires, a free tier with no persistent disk whatsoever, or needing separate infrastructure (like AWS EFS) bolted on just to persist one SQLite file. Local + a tunnel is genuinely free, zero extra maintenance, and gives a real shareable HTTPS link.

Prediction & Statistics

How does "Honest" mode's prediction actually work?

A 90% Student-t prediction interval from the user's own logged cycle lengths: mean ± t(0.95, n−1) · s · √(1 + 1/n), sample std with n−1 denominator. Needs at least 3 completed cycles — below that it says "not enough data," never a fabricated number.

Why a t-interval, not a simple percentile range or a Bayesian prior?

An empirical percentile interval on raw lengths has real coverage of roughly (n−1)/(n+1) at small n — so a "90%" interval could actually cover closer to 50% of the time at n=3, misleadingly confident. A Bayesian population prior would narrow the interval using assumptions beyond the user's own logged spread, breaking the "built only from your own data" claim and making the validation partly circular. The t-interval has the stated coverage under reasonable assumptions at every n, and naturally narrows as more cycles accumulate.

How was the interval actually validated?

Against a synthetic simulator with known, generated ground truth — realistic cycle-length distributions calibrated from a real published study, not guessed numbers. Predict at every point from 3 cycles onward across 100 simulated users, pool thousands of predictions, and check ~90% actually contain the true next date. The pass/fail gate runs on regular-cycle data only, since the method doesn't claim to handle irregular cycles; that number is recorded as informational, not a gate.

Why keep "Simple" mode at all, if "Honest" is better?

It's a deliberate baseline — literally what most commercial trackers do (a single point-estimate date). Keeping it side by side with Honest mode makes the point of the whole project visible by contrast, not just claimed in the README.

ML & Explainability

Why Random Forest for the irregularity classifier, not a neural net?

Small tabular dataset — a neural net would be overkill and harder to explain for no benefit. Random Forest pairs with SHAP's TreeExplainer, which is fast and exact for tree models, versus the slower, approximate KernelExplainer needed for other model types.

Why validate the classifier on synthetic data first?

Same reasoning as the prediction interval — need labeled ground truth to measure recall against, and real logged data has no reliable "this cycle was actually irregular" label. The simulator plants a known irregular fraction so recall (≥0.80 bar) can be checked against something actually known to be true.

What does SHAP actually add here?

Turns "the model flagged this" into "the model flagged this because of X" — a per-flag, per-feature explanation, not just a yes/no label. That's the core differentiator from a black-box flag.

Privacy & AI Usage

Where does this app call an external AI API, and why only there?

Deliberately minimal. Explain My Trend sends only pre-computed aggregate numbers (never raw logs) to turn stats into a sentence — a genuine language task. Lifestyle-Link Finder and Remedy Effectiveness were kept off the API on purpose: "does X correlate with Y in your data" is a statistics question, not a language one. Routing it through an LLM would mean the AI guessing at a pattern with no real computation behind it — breaks the core rule that every result traces to an actual statistic.

How is partner read-only access actually enforced?

At the database query layer, not the UI. A partner-scoped query function is built to be structurally incapable of writing — hiding an edit button in the UI doesn't stop a direct function or request from writing anyway; enforcing it where the data is fetched does.

Testing & SDD Process

Why were test files written before the implementation code existed?

Spec-driven development — tests encode the acceptance criteria as the build target, not a check bolted on after. For the two local-stats features, expected numbers were hand-computed independently, not derived by re-running the same formula inside the test — e.g. a deliberately planted mean difference with a hand-calculated Welch's t-statistic — so the test catches a shared bug even if the implementation uses the exact same flawed logic.

What's the actual SDD workflow being followed?

Spec (goals, non-goals, acceptance criteria) → Plan (ordered phases, each with its own acceptance criteria and explicitly flagged risks) → implement one phase at a time → stop and review the diff before the next phase. Scope changes get written back into the spec explicitly, never silently absorbed into code.
